# Fix the feedback loop, not the games

HydrogenVM does not need a new architecture to escape one-game-at-a-time debugging; it needs a cheaper way to see why a game failed and a way to stop the same class of bug from recurring. The engine is a touchHLE-style design: a JIT-less ARMv7 interpreter runs only the app binary, and roughly 56k lines of hand-written C++ stand in for iOS itself. Compatibility is therefore decided by the breadth and honesty of that hand-written surface, not by the CPU. The project's own history shows the pattern: of 172 hand-classified fixes, almost none were game-specific (1) or CPU bugs (2), while libc/C++ ABI (23%), OpenGL ES (23%) and Foundation/UIKit/ObjC (22%) dominate. Each game simply hits a different hole in a long shared tail first. Static import coverage is already near-complete on the three apps tested, so counting missing symbols will not find the next win. What slows the work is attribution (missing APIs silently return 0, crashes carry an imprecise PC, no call-site record) and the loop (a 25-30 minute macOS build plus a manual iPhone test). The recommended plan is: make runs trustworthy and diagnosable first (days), make stubs honest and track failures in a cross-game ledger second, then run class-level campaigns on the four recurring bug families. Wholesale replacement of the hand-written layers with real Apple code is the main thing to avoid. Evidence is thinner in three places: touchHLE internals, the subjective failure classification, and the 3-app corpus; all are flagged below.

## The engine is a name-lookup table over a hand-written iOS

Everything starts with `hvm import`, which unzips an IPA, followed by a `Process` that registers about 19 hand-written modules and loads the Mach-O *alone*. No system dylib exists; every import is bound by bare symbol name to a C++ function sitting in a reserved address window (0xFFFF0000 upward), or to a guest-visible ObjC class the host synthesises ([Process.cpp](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/src/runtime/Process.cpp), [ARCHITECTURE.md](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/docs/ARCHITECTURE.md)). The dylib ordinal is recorded but never used. The loader therefore judges only "found or not found", never "behaves correctly". The CPU is a lazy block-decoding threaded interpreter: guest basic blocks become 32-byte `Op` records dispatched to precompiled C++ handlers, so no machine code is generated at runtime and no JIT entitlement is needed ([Engine.cpp](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/src/core/cpu/Engine.cpp)). It covers ARM, Thumb-2, VFP and integer NEON, and runs guest memory in a 4 GB reserved arena with software 4 KB permissions that handlers never check.

The framework layer is the real project. A fresh build with no app loaded exposes **4,038 symbols (2,888 functions, 1,150 data), 252 ObjC classes, 3,573 registered methods, and uses 6,454 of 16,384 HLE slots** (research-team census of `libhvm_core.a` at HEAD `ff235bd`; the repo's own `build/` was stale). Of about 64k hand-written engine lines, the runtime is roughly 56k and the CPU core under 6k. libSystem and the GCC 4.2 libstdc++ ABI (including in-memory `std::string`/RB-tree layouts and SJLJ exceptions) are rewritten by hand; Foundation, UIKit, CoreGraphics and QuartzCore are re-implemented rather than bridged; the only table-generated family is the 267-entry OpenGL ES forwarder to the host GPU ([hostgl_spec.txt](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/tools/hostgl_spec.txt)). Several frameworks are deliberately thin: StoreKit, GameKit, iAd and UIWebView return nil or errors; CAAnimation fires completion callbacks with no interpolation; networking is offline by design. Every game sees one fixed persona, an iPhone 5 on iOS 6.1.

Two behaviours explain why failures look arbitrary. First, a missing C function stops the app in strict mode but, with keep-going, **returns 0 in r0/r1 and continues**; a missing ObjC class becomes a placeholder that returns nil to every message even in strict mode; missing data symbols become 64-byte zero blocks ([Process.cpp](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/src/runtime/Process.cpp)). Second, no generic fallback exists: nothing implements an unknown selector from its type encoding, and there is no syscall passthrough, so a raw `svc` crashes the process. The codebase also contains a handful of plausible-lie answers (`mprotect` returning 0, `dlopen` always succeeding, `AVAsset` always playable, occlusion queries always reporting 1). These contradict the project's own "never fake success" rule ([GEMINI_HANDOFF.md](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/docs/GEMINI_HANDOFF.md)).

## Per-game debugging is a long tail of shared holes plus a slow, blind loop

The 319 commits (18-29 October 2026) give a rare, complete record. Hand-classifying every `src/`-touching fix into 172 items across 100 commits yields: libc/libc++/pthread 40 (23%), OpenGL ES 39 (23%), Foundation/UIKit/ObjC 37 (22%), audio 17 (10%), file/bundle/loader 12 (7%), threading/lifecycle 10 (6%), memory/arena 9 (5%), CoreGraphics 5 (3%), CPU/ISA 2 (1%), game-specific 1 (1%). Adding 36 open draft PRs gives the same shape (the notes tally 205 items; this report does not rely on that combined figure). The ledger script reproduces these counts; the classification itself is one rater's judgement (see the last section).

Two readings follow. The "per-game" cost is not per-game *code*: only the Tiny Tower keychain sync branches on a title ([Security.cpp](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/src/runtime/foundation/Security.cpp)), so the project enforces its no-special-cases rule. The cost is per-game *discovery*. Clumsy Ninja alone produced about ten GL-context fixes; about 15 of the 40 libc items are the GCC libstdc++ ABI cluster, which keeps resurfacing across Angry Birds, Minion Rush, Terraria, Army of Darkness and Minecraft Story Mode; and the Unity/Mono startup bundle (stat layout, `sigaction` delivery, `dlopen(NULL)`, `getpw*`, audio ASBD, semaphore abort) hit Bad Piggies, Hungry Shark, Survivalcraft, Subway Surfers and RETRY together. The CPU is not the bottleneck: three independent ISA-bug hypotheses were rejected as non-bugs, and the interpreter's own correctness tests are the most systematic part of the repo.

Static census data confirms that missing imports are not the main problem. On the three IPAs in the repo, an oracle program that constructs a `Process` and queries the symbol and class tables found **0 missing symbols and 0 missing classes for Angry Birds, 0 missing symbols and 7 missing/stub classes for Tiny Tower (GameKit, UILocalNotification), and 12 missing data symbols and 2 missing classes for Art of Glow**, with the rest being selectors on stubbed frameworks (research-team measurement; scripts in the notes' `work/` folder). The open P0 items in the project's own triage are semantic: 108 failing GLSL programs in an Unreal game, a roughly 219 s host SIGSEGV, a world-load crash only on 16 KB-page devices, and EAGL context ownership ([TRIAGE_2026-10-28.md](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/docs/dev-system/TRIAGE_2026-10-28.md)).

The loop is the multiplier. Merged PRs took a median of 3.4 hours, but anything device-dependent took days: Minion Rush about 3.1 days and six attempts, Bad Piggies about 2.2, Goat Simulator about 10 days with ten-plus drafts and nothing merged. A device check needs a `[mac]` build (about 25-30 minutes, cancelled by the next push) and a manual sideload and batch run; 27 of 68 consecutive `[mac]` pushes landed within 30 minutes of each other ([GEMINI_HANDOFF.md](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/docs/GEMINI_HANDOFF.md)). Agent sandboxes often lack the IPAs or toolchain: 13 of 36 open drafts say their tests were inferred or not run. Blind fixes regress: commit `6884670` bundled five changes written without running the games, and four missed their goal; the stat-layout change `c28702f` broke seven games and was reverted 4.6 hours later; `3fde256` repaired a path change after 34 of 46 device runs crashed. The shared **quit/teardown bug** touches at least eight games, has had about nine fix attempts, and contaminates sequential batches (a leaked arena made 8, then 18, of 46 runs fail with "failed to reserve 4 GB"), so the status of many games is simply unknown.

Diagnostics exist but stop short. The repo has a missing-API log, `hvm_probe.py` severity ranking, 13-check device reports and crash bundles with registers and a 24-frame backtrace. It lacks call-site-aware missing-API records (the log is deduplicated by name with no caller or count), a ring of recent HLE/ObjC/GL calls, ObjC IMP symbolication, and an exact fault PC (reported as the block start; backlog item B-102). A returned 0 moves the failure downstream, which is why diagnosis is manual ([hvm_probe.py](https://github.com/lawsharley0-cyber/HydrogenVM/blob/main/tools/hvm_probe.py)).

## What comparable projects do, and what transfers

touchHLE is the closest relative: a Rust high-level emulator that runs only the app binary and reimplements Foundation, UIKit, OpenGL ES and OpenAL ([README fork](https://github.com/nighto/touchHLE), [Wikipedia](https://en.wikipedia.org/wiki/TouchHLE)). Its unimplemented-function policy is to panic loudly with the symbol name and a stack trace, which users then paste into issues ([issue #504](https://github.com/touchHLE/touchHLE/issues/504)); its source shows lazy-bound unknowns halting with "Call to unimplemented function" while missing non-lazy symbols only warn ([dyld.rs](https://github.com/touchHLE/touchHLE/blob/a3e44f7784beb4415d8145b0288f6916b90d975e/src/dyld.rs)). It replaced a static supported-apps list with a crowdsourced database at v0.2.1 ([release notes](https://github.com/hikari-no-yume/touchHLE/releases/tag/v0.2.1)), and its releases added tens of working apps each as shared features landed, reaching "over 300" apps rated 3+ stars ([RetroHandhelds](https://retrohandhelds.gg/touchhle-now-compatible-with-300-early-ios-games/)). Its scope is narrower than HydrogenVM's ambition: games only, iPhone OS 2.x to 4.0, 64-bit "never" ([README fork](https://github.com/nighto/touchHLE)). The lesson is not "reimplement more" but that its scaling came from a shared-framework focus, a loud-failure policy and a public telemetry loop. HydrogenVM targets iOS 6.1-era 32-bit apps, a much larger and later API surface, so it should expect a slower tail than touchHLE's early releases.

Other projects teach three transferable strategies. Library forwarding, as in Box64's wrapped native libc/GL/SDL ([README mirror](https://github.com/andrerh/box64)) and FEX thunks ([FEX 2208](https://fex-emu.com/FEX-2208/)), is what HydrogenVM's HostGL path already does for OpenGL ES; FEX also documents the pitfalls (pointer ownership, function-pointer marshalling), which map onto HydrogenVM's GL-context threading bugs. Compatibility databases are universal among HLE projects: RPCS3 reports 75.33% of 3,559 tracked titles playable ([TechSpot](https://www.techspot.com/news/113147-ps3-emulator-shouldnt-exist-can-now-play-75.html)), and Xenia tracks one GitHub issue per title with state and subsystem labels ([xenia game-compatibility](https://github.com/xenia-project/game-compatibility/issues)). Wine's stub convention separates "hard" stubs from "soft" stubs that do nothing, prints a FIXME once, and advises checking real behaviour before filling in ([wine-devel](https://mail.winehq.org/mailman3/hyperkitty/list/wine-devel@winehq.org/thread/XZDTM5TQMSXK6BNGAYJLCTO4OXN76T4O)). The fourth strategy, running the vendor's real libraries on a translator (Rosetta 2, Android's NativeBridge), works only because the vendor ships target-ISA libraries; for 32-bit iOS those live in a shared cache whose redistribution terms we could not confirm from a primary source (treat as an open legal question, not settled) ([Apple Platform Security](https://support.apple.com/guide/security/secebb113be1/web)), a point I could not confirm from a primary licence source. Darling, which reuses Apple's open-source dyld, libc and XNU while reimplementing higher frameworks, shows reimplemented GUI stacks stay slow even after years ([Wikimili](https://wikimili.com/en/Darling_(software))).

No source showed any project auto-generating *behaviour* from SDK headers. Darling generates stubs with `darling-stub-gen` but not constants ([Darling docs](https://docs.darlinghq.org/contributing/generating-stubs.html)). That limits what "better path" can mean: header-driven generation can give a coverage denominator and typed stubs, not working frameworks.

## Prioritised plan: observability, honesty, then bug-class campaigns

Effort figures below come from the research team's estimates; none were measured. Payoff is relative to how often the failure class recurs in the project's history.

| Priority | Action | Effort | Payoff |
|---|---|---|---|
| 1 | Root-cause and isolate teardown: add a last-N call ring first, then fix B-116; make the on-device batch tester isolate each game's arena | days to 1 week | Very high: unblocks trustworthy batch results for 8+ games |
| 2 | Call-site-aware missing-API record (count, first 8-12 frame backtrace, time since launch), a "tainted run" flag after the first missing hit, ring buffer of the last ~256 HLE/ObjC/GL calls in the crash bundle, ObjC IMP symbolication | 3-6 days | High: turns "log once, return 0" into a causal chain; cuts manual `--trace` sessions |
| 3 | Stub registry with status (Real/Approx/Stub/Unavailable) and provenance, plus a lint for constant-success bodies and capability queries returning YES; report "passed with N stub hits" | 2-4 days | High: stops fake successes from relocating failures |
| 4 | Permanent `--dump-support` manifest, census preflight per IPA, and a hash-keyed cross-game ledger with failure-class tags | 3-4 days | Medium now, high once all 18 library apps are censused |
| 5 | Class campaigns, one at a time: (a) GCC libstdc++ ABI conformance guests; (b) a single documented GL context/thread/FBO model; (c) a Unity/Mono startup checklist; (d) libc formatting/memory property tests against glibc | 1-3 days to 2 weeks each | High: attacks the recurring ~60% of fixes at once |
| 6 | Corpus-gated `git bisect` wrapper and a ring-buffer GL capture | 2-3 days | High while many parallel PRs land |
| 7 | Semantic event record/replay (touches, timers, file reads, RNG, thread order) | 1-2 weeks, after a determinism audit | High for long-session and device-only crashes (Goat's ~219 s SIGSEGV) |
| 8 | Port selected objc4 tests as Test Lab cases; vendor Apple CF leaf algorithms (plist, calendar) only after a licence decision | 3-5 days / 2-4 weeks | Medium-high |

The ordering rests on one argument: nothing else is trustworthy until runs are. Priority 1 and 2 convert the existing probe sweep from a list of symptoms into a ranked list of causes, and their unit-level parts need no IPA to build and test, but the probe and on-device batch checks need a game or equivalent guest fixture, so those run on a runner with the IPAs. Priority 3 matters because the stub that "succeeds" is what turned Hungry Shark and Bad Piggies audio aborts into a misdirected hunt (their real causes were the RemoteIO thread model and `mmap(MAP_FIXED)`). Priority 5 is where the history says the volume is. Two items are my judgement rather than the notes' direct findings: running the Linux harness with 16 KB commit granularity to close the Linux/device gap (the notes document the gap, 4 KB vs 16 KB pages, but not this fix), and treating the dual software/HostGL OpenGL stacks as a risk to be narrowed, since the software path is where Goat's 108 GLSL failures and 65 ms frames sit while the GPU path leans on the deprecated OpenGLES.framework (a Metal backend is only a roadmap item).

## What not to do

Do not replace libc, the ObjC runtime or CoreFoundation wholesale with Apple's open-source code. The published trees are far newer than iOS 3-6 (objc4-951 is a modern-runtime-only tree; Libc 1752 carries post-iOS-6 behaviour), depend on private kernel and dyld interfaces, would execute under the interpreter, and carry APSL 2.0 obligations to publish modifications; use them as test oracles and for leaf algorithms after a licence review (not legal advice) ([APPLE_LICENSE in objc4](https://github.com/apple-oss-distributions/objc4), [CF](https://github.com/apple-oss-distributions/CF)). Do not invest in CPU fuzzing or lock-step against Unicorn ahead of the above; the interpreter accounts for 1% of fixes, and QEMU itself disagrees with real devices on about 5.6% of instruction streams, mostly UNPREDICTABLE behaviour ([INSDET](https://arxiv.org/pdf/2105.14273v2)). Do not rank work by import frequency at current corpus size: a leave-one-out test on three apps predicted 0, 1 and 1 of the held-out gaps, because 65% of imported symbols belong to a single app. Do not treat keep-going output as a compatibility verdict; it is discovery only. Do not add more title-keyed code (the Tiny Tower keychain sync, whose `gameData` match also fires for any app with such a service name, should be generalised or removed), and do not redo the 96-byte stat layout, which broke seven games. Do not batch unverified changes into one push, and do not accept a fix on Linux alone: three regressions reached the phone that way. Do not resume Clash Royale server restoration (about 10% of commits, parked on 2026-10-23) until the shared base improves. Do not trust the docs' test counts or architecture summaries as current state; they drift (ARCHITECTURE.md still says GL is software-only).

## How much to trust this

The weakest links are these. touchHLE facts come from release pages, README forks and Wikipedia; I could not read its dev docs, source layout beyond `dyld.rs`, or its app database, so its current app count, CPU core design and handling of unknown *Objective-C selectors* are unverified, and release years are ambiguous. The failure taxonomy is one reader's classification of commit messages; items could fall in two classes, early bulk commits are under-split, and no second rater checked it. History spans only ten days, so rates may reflect bring-up rather than steady state. The import and selector census covers three apps, and the selector check ignores which class receives a message. Device-side state after 25 October comes from handoff prose, not reports. The "trivial stub" count (about 459) is a name-pattern heuristic, and effort estimates are unmeasured. The memory note giving "iOS 20" as the minimum disagrees with the project's iOS 26.0 deployment target, which I used. Whether the two Minecraft entries are one game is unresolved.

## Conclusion

The central finding is that HydrogenVM's slowness is mostly a measurement problem, not a coverage problem: static resolution is close to complete on the apps measured, the CPU is not the cause, and game-specific code is nearly absent, yet each failure costs days because the engine returns plausible zeros, reports imprecise faults, and cannot cheaply say which earlier missing call caused a later crash. That reframes the goal from "implement more APIs" to "make every failed run produce a ranked, causal, cross-game record", after which the four recurring bug families (C++ ABI, GL context model, Unity/Mono startup, teardown) can be closed as classes.

What would change this advice: a census of all 18 library apps (if most missing items concentrate in a few stubbed frameworks, a framework-level "honest minimal implementation" decision would beat incremental fixes), and a clean whole-library run after the teardown fix (many "state not recorded" cells would resolve and show which classes truly dominate).
