# Guest C++ Runtime Libraries — Licensing & Distribution Note (S3)

**Date:** 2026-11-03  
**Initiative:** Guest-Dylib Initiative (`Refs #311`)  
**Status:** Owner review required before bundling any built `.dylib` in a distributed HydrogenVM `.ipa`.

---

## 1. Purpose

HydrogenVM's Guest-Dylib experiment (`ProcessConfig::guestLibs`) loads 32-bit ARMv7 iOS (`MH_DYLIB`) builds of open-source C++ runtime libraries into guest memory in place of hand-written per-symbol C++ stand-ins.

Per repository policy (`AGENTS.md`):
- Built `.dylib` binaries are **never committed to git**.
- `tools/guestlibs/build_guestlibs.py` builds them reproducibly into an external output directory (`--out <dir>`) or private fixture store (`HVM_FIXTURE_ROOT`).
- Shipping any third-party runtime binary inside an iOS `.ipa` bundle requires an explicit licensing decision from the project owner.

## 3. Distribution & Attribution Obligations for an iOS App Bundle

### 3.1 Target 2: `libc++.1.dylib` and `libc++abi.dylib` (`Apache-2.0 WITH LLVM-exception`)

- **Permissive binary redistribution:** `Apache-2.0 WITH LLVM-exception` (and the legacy UIUC/NCSA license) permits redistributing compiled `.dylib` binaries inside a proprietary or open-source iOS `.ipa` bundle without copyleft or source-disclosure obligations on HydrogenVM itself.
- **Required obligations if shipped in `HydrogenVM.ipa`:**
  1. Include the full text of the `Apache-2.0 WITH LLVM-exception` (and UIUC/NCSA) license in HydrogenVM's third-party notices (`Settings -> Acknowledgements` or bundled `THIRD_PARTY_NOTICES.txt`).
  2. Retain upstream copyright notices from the LLVM Project.
  3. State any build modifications made by `tools/guestlibs/build_guestlibs.py` for ARMv7 iOS cross-compilation.

### 3.2 Target 1: `libstdc++.6.dylib` and `libgcc_s.1.dylib` (`GPLv3 + GCC Runtime Library Exception`)

- **Runtime Library Exception scope:** The GCC Runtime Library Exception permits linking "Target Code" generated by any compiler not used to circumvent the GPL, and distributing the resulting libraries alongside a program, provided the "Compilation Process" itself is Eligible.
- **Copyleft / source-offer obligations on the `.dylib` files themselves:**
  1. Even when the GCC Runtime Library Exception shields the host emulator (`HydrogenVM`) and the guest `.ipa` from GPL copyleft propagation, distributing binary copies of `libstdc++.6.dylib` and `libgcc_s.1.dylib` inside `HydrogenVM.ipa` triggers **GPL Section 6** obligations **for the `libstdc++` and `libgcc` libraries themselves**:
     - Include a copy of the GPL and the GCC Runtime Library Exception text in the app bundle / UI acknowledgements.
     - Provide the Corresponding Source (the exact pinned source archive + `tools/guestlibs/build_guestlibs.py` build scripts and flags) alongside the binary distribution or via a durable written offer / download link.
  2. **App Store vs Sideloaded `.ipa` consideration:** Apple's App Store terms conflict with strict GPLv3 anti-DRM clauses (`Section 3`), whereas sideloaded unsigned `.ipa` distribution with full source access in the GitHub repository satisfies Corresponding Source availability if the exact tarball used to produce `libstdc++.6.dylib` / `libgcc_s.1.dylib` is archived and mirrored alongside the release.

## 4. Owner Decision Gate

> **Escalation to Owner:**
> 1. **Target 2 (`libc++.1.dylib` + `libc++abi.dylib`, `Apache-2.0 WITH LLVM-exception`):** Low legal friction; requires only standard attribution in third-party notices if S6 passes the technical gate.
> 2. **Target 1 (`libstdc++.6.dylib` + `libgcc_s.1.dylib`, `GPLv3 + GCC Runtime Library Exception`):** Requires owner sign-off on whether to (a) ship `libstdc++.6.dylib` / `libgcc_s.1.dylib` with full GPL + Runtime Exception notice and mirrored Corresponding Source, (b) keep Target 1 external in the user's private store / developer build step, or (c) implement an `Apache-2.0 WITH LLVM-exception` ABI compatibility shim layered over `libc++abi` for legacy `_ZNSs*` / `_ZNSt8ios_base*` symbols.
